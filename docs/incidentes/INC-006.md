# INC-006: «Publicar en Cloudflare» en rojo 3 veces seguidas (6 nov 2026)

- **Detección:** runs 42192992880, 42194778238 y 42196002199 del workflow `deploy-cloudflare.yml` en `main`, 6 nov 2026 09:10–09:39 UTC. Último deploy bueno: 42191177592 (08:55 UTC, `bb7f3f7`).
- **Entorno:** producción, Worker `travel-puzzle-web`, wrangler 4.155.0.

## Lo que pasó en cada run (logs de `gh run view --log-failed` y pasos del job)
| Run | Commit (PR) | Paso que falló | Error exacto | ¿Producción cambió? |
|---|---|---|---|---|
| 42192992880 | `d2f2ed7` (#110) | Subir versión (sin tráfico) | `edge-preview` → `An unknown error has occurred [code: 10013]` (API de Cloudflare) | No |
| 42194778238 | `77b081b` (#112) | Subir versión (sin tráfico) | `GET …/workers/subdomain/edge-preview -> 503 Service Unavailable` · `no healthy upstream` | No |
| 42196002199 | `15e7cfd` (#126) | Secretos del Worker (después de Publicar) | `Secret edit failed. You attempted to modify a secret, but the latest version of your Worker isn't currently deployed.` | Sí: versión `c8f943d3` al 100 % |

Los dos primeros NO son el error de secretos: fueron fallas pasajeras de la API de Cloudflare (los PR #125, #127 y #128 fallaron en el mismo paso y a la misma hora: 09:12, 09:16, 09:26, 09:29, 09:31). El gate funcionó: no se publicó nada.

El tercero sí publicó: humo antes de publicar verde (09:37:15–09:38:29), `versions deploy c8f943d3@100%` OK (09:38:32). Luego `secret put` de FREETOUR_EMAIL, FREETOUR_PASSWORD y GATEWAY_SECRET OK y el de RESEND_API_KEY falló a las **09:38:41.72**. La prueba de humo de producción y el regreso automático **se saltaron** (el paso anterior falló).

## Evidencia de la causa
- PR #128 (`ops/primera-pieza-encender`, run 42195127054, intento 3) subió su versión de prueba **sin tráfico** `7ae6f7a4` (alias `pr-128`) a las **09:38:41.70**, 20 ms antes del error.
- Desde ese momento la «última versión» del Worker es la del PR, no la desplegada, y `wrangler secret put` se niega. Así lo explica wrangler: se niega «para evitar un deploy accidental».
- **Casi incidente:** `secret put` crea una versión nueva a partir de la última y la despliega. Sin esa protección de wrangler, el deploy habría publicado el código del PR #128, con `PRIMERA_PIEZA_ENABLED` encendida y sin OK del PO.
- `git diff bb7f3f7 15e7cfd`: solo cambian `imports/*.json` (no los importa `src/`). En código, producción no quedó desfasada de `main`.
- `wrangler versions list` NO se corrió: no hay credencial de Cloudflare local, y un workflow nuevo solo de lectura tendría que estar en `main` para dispararlo. Los IDs y horas salen de los logs de ambos runs.

## Causa raíz (5 porqués)
1. ¿Por qué falló el run 3? Porque `wrangler secret put` se negó: la última versión del Worker no era la desplegada.
2. ¿Por qué no lo era? Porque el PR #128 subió su versión de prueba entre el `versions deploy` y el cuarto `secret put` (ventana de unos 10 s).
3. ¿Por qué hay esa ventana? Porque los secretos se ponían DESPUÉS de publicar, con un comando que trabaja sobre «la última versión» y no sobre la versión que acabamos de probar.
4. ¿Por qué se diseñó así? Venía de antes de REQ-003 (deploy directo, cuando la última versión siempre era la desplegada). Al pasar a «subir sin tráfico → humo → desplegar» y agregar versiones de PR, ese paso quedó fuera de lugar.
5. ¿Por qué ninguna prueba lo detectó? No había ninguna prueba sobre el workflow de deploy. La prueba de humo de PR no sube secretos ni despliega. Y la carrera solo ocurre si un PR sube su versión en esos segundos: con pocos PR al mismo tiempo, no pasaba.

**Causas que se suman:** (a) la subida no reintenta ante fallas pasajeras de la API (runs 1 y 2). (b) La prueba de humo de producción dependía de que todos los pasos anteriores salieran bien, así que un fallo después de publicar dejaba producción sin probar. (c) Riesgo latente: si `wrangler secret list` fallaba, el script caía a `[]` y habría regenerado AUTH_SECRET y CRON_SECRET.

## Impacto
- Para los usuarios, ninguno. Producción quedó con `15e7cfd` (= `main`; solo cambian datos de `imports/`, que no se empaquetan) y los mismos valores de secretos.
- La prueba de humo de producción no corrió en el run 3. Se corrió a mano después del incidente: `npx tsx src/scripts/smoke.ts https://travelpuzzle.com.mx` dio 18 cargas sin errores (390 y 1366 px).
- Hasta que se fusione la corrección, cada merge a `main` puede repetir el fallo cuando haya un PR subiendo su versión.

## Corrección (REQ-155)
- `deploy-cloudflare.yml`: el paso nuevo «Secretos de la versión» arma un JSON (0600, en `RUNNER_TEMP`). Los secretos suben **dentro** de la misma versión con `opennextjs-cloudflare upload --secrets-file=…` (wrangler `versions upload --secrets-file`, aditivo: los omitidos se heredan). Esa misma versión pasa el humo y se despliega por ID. Ya no se depende de cuál sea «la última versión».
- El archivo se borra con `if: always()`. Solo se imprimen nombres, y las claves generadas se enmascaran.
- El paso viejo `wrangler secret put` queda apagado (`if: ${{ false }}`) para poder regresar.
- Hasta 3 intentos de subida (espera de 30 s y luego 60 s) ante fallas pasajeras de la API.
- La prueba de humo de producción corre con `always() && steps.publicar.outcome == 'success'`, y el regreso con `always()`.
- Si `wrangler secret list` falla, el deploy se detiene: ya no se regeneran claves internas por error.
- Modo `ensayo` (workflow_dispatch): sube la versión con secretos, la prueba y **nunca** publica ni migra.
- Lógica pura en `src/ops/lib/worker-secrets.ts`; la parte de I/O está en `src/scripts/worker-secrets.ts`.
